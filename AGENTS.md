# AGENTS.md

Chrome MV3 extension (TypeScript, React, Vite + `@crxjs/vite-plugin`) that commits Overleaf project snapshots to GitHub and, behind toggles (the pull into Overleaf is on by default, reading from the tab is off), syncs in both directions through Overleaf's internal realtime protocol. That protocol is undocumented, so live sync can break whenever Overleaf changes it; **Fetch from current Overleaf project** (the ZIP route) remains the most dependable path.

`README.md` is the user guide. Its **Security** section lists guarantees users rely on. `PRIVACY.md` is the published privacy policy. This file covers architecture, protocol facts and how to verify a change.

## Architecture

Three sources become a `SourceSnapshot` (`files: ProjectFile[]`) and go through the source-agnostic diff (`src/diff/`) and commit (`src/github/commitEngine.ts`) pipeline. The GitHub branch feeds the other direction, and the local replica is not wired in:

| Source | Module | Goes to |
| --- | --- | --- |
| Manual ZIP (opt-in, see **Manual ZIP upload setting**) | `src/zip/zipReader.ts` via `src/sources/sourceManager.ts` | commit |
| Overleaf ZIP route | `src/overleaf/overleafZipClient.ts` | commit; also the pull's ZIP gate |
| Live read-only | `src/overleaf/live/liveSyncManager.ts` (content script) | commit |
| GitHub branch | `src/sources/sourceFromGitHubBranch.ts` (returns files, not a `SourceSnapshot`) | the pull into Overleaf only |
| Local replica | `src/localReplica/*` | nothing: no module imports it. The Options switch and popup card say it does nothing yet |

- **ZIP download.** `downloadOverleafZip` is a plain credentialed `fetch` from the popup or Options page (host permission, `credentials: 'include'`), not through the content script. It tries two endpoints and validates the ZIP signature. `readZipFromBytes` parses it.
- **Manual ZIP upload setting.** The UI preference `manualZipUploadEnabled` (`UIPreferences`, `src/shared/types.ts`; default `false` in `DEFAULT_UI_PREFERENCES`; stored values are coerced to a boolean in `getUIPreferences`) is set under Options -> Popup display ("Enable manual ZIP upload"). While it is off the popup renders no Manual ZIP upload anywhere: not the ready-view section, not the error view's inline picker, and not the no-tab flow (a `no-tab` phase with guidance replaces `pick-project`, whose only purpose is choosing a repo for a manual upload). While it is on, the section shows when the automatic fetch failed, when no Overleaf tab is open, or when the sub-option `alwaysShowManualUpload` is on (Options hides that sub-option while the setting is off, and the popup ignores it); `project_too_large` and `project_empty` still offer no picker. The popup alone chooses the wording: with the setting off, a failed Overleaf fetch gets `remedyForZipFetchError` when its message has no advice of its own, plus the tip `MANUAL_ZIP_OPTIONS_TIP` ("You can also turn on Manual ZIP upload in Options."). Keep recovery hints and errors in the other modules free of any mention of the manual upload.
- **Bridge.** The popup sends `LIVE_*` messages with `chrome.tabs.sendMessage`. `src/content/overleafContentScript.ts` dispatches them to `liveBridgeHandler.ts`, which uses `socketIo09.ts` (a hand-written Socket.IO 0.9 / Engine.IO 0.x client) and Overleaf's REST routes. It reads the CSRF token from `<meta name="ol-csrfToken">`; a page without one fails with `page_not_recognized`, which is not retried. The content script adds nothing to the Overleaf page and never touches its DOM. The in-page launcher button was removed (a content script cannot open the action popup in MV3), and the service worker only opens Options on install and answers `OPEN_OPTIONS` and `PING`. Each `LIVE_*` message has a `*ResponseData` type in `bridgeProtocol.ts`; the dispatcher answers a malformed request at once and returns `true` for async work.
- **Retries and duplicate writes.** `sendBridgeRequest` (`liveSyncManager.ts`) maps every `chrome.runtime.lastError` to `protocol_unavailable`. On that code it injects the content script (`chrome.scripting.executeScript`) and re-sends the same request up to 5 times, 200 ms apart. A `lastError` also covers "message port closed before a response", which happens after delivery, so a retry can replay a write that already ran. Two rules follow. A handler must never report `protocol_unavailable` after it may have written anything (use `unknown`, `network` or a typed code). Every async branch in the content-script dispatcher must `return true`, or the port closes and the request is replayed. The replace and delete messages of **Make Overleaf match GitHub exactly** are safe to replay: each re-checks the entity ID, bytes or text first, so a replayed one that already ran changes nothing. `ProjectSession` remembers what it carried out (`deletedEntityIds`, `replacedFiles`, each added only after Overleaf's 2xx), so a replay that finds the entity gone, or the replacement in place with the bytes being sent (read again and compared), answers `ok` with `alreadyDone: true` and the row reads "Deleted" / "Replaced" with "Confirmed on a second check". An entity that someone else removed is not in that memory, so its row still reads "Not deleted / Not replaced".
- **Sessions.** The pull runs on one content-script session: one socket and one joinProject for every read, write, create and upload. `OverleafBridgeSession` (`src/overleaf/live/bridgeSession.ts`) sends `LIVE_SESSION_*` messages to `ProjectSession` in `liveBridgeHandler.ts`. Reads pipeline 4 joinDocs at a time on distinct docs, writes/creates/uploads run one at a time, the socket reconnects at most 4 times, and an idle session closes after 180 s (the popup reopens it up to 2 times). The content script advertises `features: ['project-session-v1', 'mirror-v1']` in its `LIVE_PING` reply (`mirror-v1`: it handles the messages of **Make Overleaf match GitHub exactly**); a tab without `project-session-v1` (old content script) gets `bridge_outdated` ("reload the tab") before anything is written, and a tab without `mirror-v1` gets it when that option is on. The one-shot messages (`LIVE_READ_DOC`, `LIVE_WRITE_DOC`, ...) still work on a single-call session.
- **Pull from GitHub: plan, then apply** (`src/sources/pullFromGitHubHelpers.ts`, shared by the popup and the Options dev panel).
  - `planPullIntoOverleaf` writes nothing. Under the pull lock it opens the session, takes the ZIP gate if any write could follow, skips docs whose ZIP text already matches GitHub (`zipMatchesGitHub`, insensitive to line endings and to characters Overleaf can't store), reads the rest, and returns a `PullPlan` (docs to replace with the text read as their base, docs to create, binaries to upload, files that already match, files left out with the reason). The session stays open for the apply unless there is nothing to apply.
  - `applyPullPlan` runs only after the user confirms. It takes the pull lock again, takes a new ZIP gate if the plan's is older than 10 minutes (`PLAN_ZIP_BACKUP_MAX_AGE_MS`), replaces the planned docs, then creates and uploads the planned files. A plan applies once. It never re-reads GitHub, and the conflict base is the plan's read, so an Overleaf edit made after the preview fails the conflict check. `discardPullPlan` (Cancel) closes the session.
  - A path that is an uploaded file in Overleaf (a fileRef) is never "missing": it is a skipped doc row plus a left-out reason, whether or not "Also create new files" is on. (Except with **Make Overleaf match GitHub exactly**, below.)
- **Make Overleaf match GitHub exactly** (pull option; checkbox in the popup's pull section and the Options pull test panel, **remembered per Overleaf project**: `getMirrorMatchEnabled` / `setMirrorMatchEnabled` over the `mirror_match_projects` map in `chrome.storage.local` (`{ [projectId]: true }`), off for every project that isn't in it; the old global `makeOverleafMatchGitHub` key in the stored live sync settings (`experimental_config`) is dropped on read, not migrated; removing a project link or resetting clears the entries; the checkbox and the pull button stay disabled until the stored choice has been read, and while it is ticked the pull button reads "Pull and match GitHub", grey like any other button and a red outline on hover or keyboard focus). It is the one place a pull deletes or replaces anything beyond docs. GitHub is treated as the main copy: Overleaf files that aren't on GitHub are deleted, and uploaded files (fileRefs) whose bytes differ are replaced, by uploading GitHub's bytes (so `.gitignore` stays a file). Code: `planMirror` / `applyMirror` in `pullFromGitHubHelpers.ts`, `replaceUploadedFileInSession` / `deleteEntityInSession` / `hashFilesInSession` in `liveBridgeHandler.ts`.
  - *Implied settings.* A pull with it on behaves as if "Also create new files", "Include all file types" and "Allow uploading new images and other non-text files" were on, whatever is stored (`withMirrorSettings`, `pullSourceOptions`; callers must fetch GitHub with `pullSourceOptions(experimental, true)` (which also asks for the repository's `.gitignore` files) and pass `mirror: mirrorInputFromSnapshot(snapshot, repo)` to `planPullIntoOverleaf`, which applies the same settings itself).
  - *Planning (still writes nothing).* Under the same lock and session. **Names:** before anything else each GitHub path takes Overleaf's spelling when the two differ only in Unicode normalization (`alignGitHubNamesWithOverleaf`, folders and file name, exact match first; a name that fits several Overleaf entries is left out with a reason). This applies to every pull, not only the mirror, so an NFD twin is never created next to its NFC original; all mirror sets below compare NFC forms. **Replacements:** each Overleaf fileRef whose path is a file on GitHub is compared with GitHub's blob bytes: equal if the backup ZIP's size and SHA-256 match, else the bytes are read from Overleaf (`LIVE_SESSION_HASH_FILES`, SHA-256 and size only) and hashed. Only differing files are planned (`PlannedFileReplace`: path, file ID, SHA-256 of Overleaf's bytes, GitHub's bytes, and `linked` when the tree's fileRef has `linkedFileData`). **Deletions:** every Overleaf doc or fileRef whose path is not in the FULL GitHub tree is a candidate. The tree is `GitHubBranchSnapshot.treeEntries` (every entry inside the target directory, mapped with the pull's own `applyTargetDir`: blobs, folders, submodules and symbolic links, before any type, binary or UTF-8 filter), plus the parent folders of every entry and of every pulled file. Never the filtered pull list: files left out by type, binary files, non-UTF-8 files, and a doc whose GitHub twin has an extension the extension reads as non-text all exist on GitHub and are never deleted. **Kept, with the reason listed (`MirrorPlan.kept`, `MirrorKeepSource`):** an entry at or under a path GitHub has as a **submodule** (tree type `commit`) or a **symlink** (blob mode `120000`); a **build** file (`DEFAULT_IGNORE_PATTERNS`), a file matching the mapping's own **pattern**s (both matched with `isIgnored` against the project-relative path like the commit route), or a file the repository's own **.gitignore** files exclude (`src/diff/gitignore.ts`: `*`, `?`, `[a-z]`, `**`, trailing `/`, leading or middle `/`, patterns relative to the .gitignore's folder; the files read are those inside the target directory and in the folders above it, matched against the repository path; `!` negations are skipped on purpose, which keeps more). Symbolic links are never pulled in any mode (`sourceFromGitHubBranch` skips them with `SYMLINK_SKIPPED_REASON_PREFIX`, the preview lists them as left out), so a link target is never written, created or uploaded. A doc is read first and its text kept as the base (`PlannedDelete.baseText`; `isRootDoc` when it is the project's main document, from the session's `rootDocId`, joinProject's `rootDoc_id`); one that can't be read is kept and listed (`notDeleted`). A folder is planned only if GitHub has no such folder, it isn't ignored or under a submodule or symlink, and everything in it (docs, files, subfolders) is itself planned, or it is empty already (so it ends up empty); folders are ordered deepest first. Deletions are counted in docs and files: more than 20, or more than 30% of the files that count (`MirrorPlan.projectFileCount`: the project's docs and files minus the kept ones, `MIRROR_LARGE_DELETION_*`), is a large deletion.
  - *Refusals (nothing is touched).* `mirrorGitHubView` and `scopeMirrorDeletions` throw `write_back_not_safe` before any write when: the GitHub tree is truncated, or holds no file inside the target directory (an empty tree would delete everything), or the mapping looks wrong (`refuseIfMappingLooksWrong`, over the Overleaf files that are neither kept as ignored nor under a submodule or symlink, only when something would be deleted): every one of them sits in one top folder and stripping it matches GitHub better than the paths as they are (the ZIP route drops a folder that holds everything), not one has a counterpart on GitHub, or fewer than half (`MIRROR_MIN_MATCH_SHARE`) do. Each message says why and that the branch or target directory may be wrong. `sourceFromGitHubBranch` already refuses a truncated tree for every pull. An Overleaf tab whose content script predates the option (no `mirror-v1` in its `LIVE_PING` features, `BRIDGE_FEATURE_MIRROR`) gets `bridge_outdated` before anything is read.
  - *Confirmation.* Any plan with a deletion or an uploaded-file replacement asks for the typed word `delete`, whatever `requireConfirmationBeforeWriteBack` says (it supersedes `replace`); a large deletion asks for `delete N`, N being the exact number of files to be deleted. `pullConfirmationWord`, `isPullConfirmationTyped(text, plan)` (trimmed, any case, spaces collapsed). `applyPullPlan(plan, onProgress, typedConfirmation)` enforces it too, before touching the plan, so a UI bug can't skip it.
  - *Apply order.* Doc replaces, creates and uploads first (unchanged), then uploaded-file replacements, then deletions of docs and files, then folders deepest first. The pull lock, the ZIP gate (retaken if the plan's backup is older than 10 minutes) and "a plan applies once" are unchanged, and nothing is re-read from GitHub. Deletions are in the ZIP gate's `mayWrite`, so a plan that only deletes still takes the backup first.
  - *Mirror off:* none of the mirror steps run. `PullPlan.mirror` is `null`, the outcome has no `fileReplaceResults` / `deleteResults` keys, and the plan, rows, typed word and wording are what they were, apart from two changes that hold for every pull: GitHub symbolic links are skipped (never created or uploaded) and listed as left out, and a GitHub name that differs from an Overleaf one only in Unicode normalization is the same file.
- **Write paths and their gates.** Do not add a path that skips these.
  - *Replace a doc*: `writeSelectedFilesBackToOverleaf` (`overleafWriteBack.ts`). Pull lock (held by the caller during a pull, taken by the function when it runs standalone), extension allow-list, ZIP gate, fresh read, `conflictDetector` against the base text, `overleafOt.diffToOps` (one delete and one insert), version-checked `applyOtUpdate` (the content script refuses with `remote_changed` if the version moved), read the doc again to verify.
  - *Create a doc*: `createDocInSession` in the content script. Pull lock, ZIP gate, allow-list, `runProjectMutation`. It is create-only: a name already in the session tree is `already_exists`, and Overleaf refuses a taken name on POST `/doc` (also mapped to `already_exists`). The content is seeded with one insert and read back to verify.
  - *Upload a binary*: `uploadBinaryInSession`. Pull lock, ZIP gate, `runProjectMutation`. Create-only, and it is the only guard, because Overleaf's upload route replaces an entry with the same name. Right before the POST it re-checks a fresh listing (`GET /project/:id/entities`, a plain REST read that does not count against the join limit) and refuses with `already_exists` if the path is taken, or with `write_back_not_safe` if the listing cannot be read.
  - *Replace an uploaded file* (**Make Overleaf match GitHub exactly** only): `replaceUploadedFileInSession` (`LIVE_SESSION_REPLACE_FILE`). Typed `delete` (enforced in `applyPullPlan`), pull lock, ZIP gate, `runProjectMutation`. Before the POST it requires all of: the session tree re-read if older than 15 s or after a rename or move was seen (`MIRROR_TREE_MAX_AGE_MS`, `ProjectSession.ensureTreeFresh`, one `joinProject`), and the entity at the path in it still being the planned file ID (a file renamed away, or deleted and uploaded again, has another); a fresh `GET /project/:id/entities` listing the path as a `file`; and the file read again by the planned ID (a 404 means it is gone) with the planned SHA-256. Then it uploads (the same POST that replaces an entry of that name, with the folder ID from the fresh tree) and reads the new file back by the new ID to compare it with the bytes sent. If Overleaf answers that the replacement is an editable doc (`entity_type: 'doc'`), the row says so. A refusal is `remote_changed` (changed after the preview) or `write_back_not_safe` (could not check), both rows "Not replaced".
  - *Delete a doc, uploaded file or folder* (same option): `deleteEntityInSession` (`LIVE_SESSION_DELETE_ENTITY`). Same gates and the same fresh tree check: the entity at the path must still have the planned ID. A doc is joined again and its text hashed against the plan's base (`expectedSha256`): an edit made after the preview means "Not deleted: this file was edited in Overleaf after the preview, so it was kept", with no DELETE sent. An uploaded file is deleted only if the listing still shows the path as a `file` with the planned ID. A folder is deleted only if it is empty in the fresh tree and the listing shows nothing under it, never relying on Overleaf's recursive delete (the popup also skips a folder after any of its planned contents was kept). A 404 on the DELETE reads "Not deleted: Overleaf no longer has it". After a 5xx or a timeout the row says it is unknown whether it was deleted and to run the pull again; a row says "Deleted" only after a 2xx.
  - A row never claims a write that did not happen: after a 5xx, a timeout or a network error the row says the outcome is unknown and to run the pull again. Only a 4xx on an upload, doc or folder POST means nothing was added.
- **Locks.** Two layers, both per project.
  - `src/overleaf/live/projectPullLock.ts`: one pull (or Options write-back test) per project in the browser, from the popup or Options. A record `{ owner, expiresAt }` under `pullLock:<projectId>` in `chrome.storage.session` (cleared when the browser quits), checked and set under a Web Lock. TTL 90 s, renewed every 20 s, so a popup killed mid-run frees it. Refusal is `project_busy`. Planning and applying each take it; none is held while a preview is open, so another pull can run in between, and the conflict check is what catches its edits.
  - `runProjectMutation` (`liveBridgeHandler.ts`): a promise chain per project in one tab that serializes write, create and upload (including their folder POSTs and the verify read). It stops two pulls on the same doc version from both applying the same change, which Overleaf would not reject but duplicate. It cannot see other tabs, hence the pull lock.
- **Storage.** `src/storage/extensionStorage.ts` holds `project_links`, which maps each Overleaf project ID to its own repo config and token. It also holds the global live sync settings (stored under `experimental_config`; defaults in `DEFAULT_EXPERIMENTAL_CONFIG`, `src/shared/constants.ts`: `experimentalLiveSyncEnabled` and `overleafWriteBackEnabled` are on by default, by the owner's decision; `liveReadOnlyPullEnabled` and `localReplicaEnabled` are off; the defaults reach only a profile that never saved the settings, and stored values are kept without migration) the per-project "Make Overleaf match GitHub exactly" choice (`mirror_match_projects`, see that section) and the legacy single-config migration.
- **Errors.** Codes are typed. `OverleafZipFetchErrorCode` is in `src/overleaf/overleafZipClient.ts`; `LiveSyncErrorCode` is in `src/overleaf/live/types.ts`. Add a code instead of throwing a bare string. The popup shows a recovery hint for each as "What to try:". Messages say in plain words what happened and whether anything changed; the raw cause goes once, after "Details:" (`asDetail`). Recently added: `project_too_large` and `project_empty` (ZIP; an export beyond the ZIP reader's limits, or with no files, offers no manual-ZIP fallback because a manual ZIP hits the same limits), and `already_exists`, `project_busy`, `not_attempted` (an earlier operation lost the tab, so this one was never sent), `page_not_recognized`, `bridge_outdated`, `bridge_session_lost` (live). The mirror option adds no code: its refusals reuse `write_back_not_safe` (refused before a write: unsafe GitHub tree or mapping, backup failed, could not re-check Overleaf), `remote_changed` (the entity changed after the preview) and `bridge_outdated` (content script without `mirror-v1`).
- **Line endings.** `src/shared/lineEndings.ts` (`normalizeLineEndings`, `\r\n?` to `\n`). Wherever GitHub text is compared with, or sent to, Overleaf it is normalized first: plan (read compare, replace text, create content), `zipMatchesGitHub`, `writeSelectedFilesBackToOverleaf` (conflict check, write, verify), `conflictDetector` (the "unchanged" test only; remote-vs-base stays byte-exact), `createDocInSession` (seed and verify). The reverse direction is in `diffEngine.ts`: a text file whose git blob SHA differs from GitHub's is unchanged when the SHA of its LF, CRLF or CR form matches (`gitBlobShaMatchesIgnoringLineEndings`), using only the tree SHA already fetched.
- **Characters Overleaf can't store.** `toOverleafStorableText` (`src/shared/lineEndings.ts`) is `normalizeLineEndings` plus every UTF-16 surrogate code unit replaced with U+FFFD, exactly as Overleaf does on insert (see **Overleaf protocol: confirmed facts**). It replaces `normalizeLineEndings` for GitHub text in: the plan (read compare, replace text, create content), `zipMatchesGitHub`, `writeSelectedFilesBackToOverleaf` (write and verify), `conflictDetector` (the "unchanged" test only), `createDocInSession` (seed and verify). A doc whose only difference from GitHub is such characters is skipped with `UNCHANGED_UNSTORABLE_MESSAGE`; a file with a real change plus such characters is written (the plan holds the storable text, so verify passes) and its row, and the preview line, say the characters become U+FFFD (`hasUnstorableChars`).
- **GitHub files that aren't valid UTF-8.** `sourceFromGitHubBranch` decodes text with `decodeUtf8Text` (fatal attempt first; BOM kept) and flags a file whose bytes are invalid with `ProjectFile.invalidUtf8`; its `text` is the lossy decode (U+FFFD for the bad bytes). The pull rule: such a file is never written or created. If Overleaf already holds exactly that lossy text (checked against the ZIP, else a read) it counts as already matching, with `UNCHANGED_NOT_UTF8_MESSAGE`, so it isn't flagged every time. Otherwise (Overleaf holds something else, possibly the properly decoded text, or has no such doc) it is left out of the plan with `NOT_UTF8_REASON` in the preview's left-out list and `NOT_UTF8_ROW` in the result, whether or not "Also create new files" is on. Re-saving the file as UTF-8 on GitHub makes it pullable.
- **Overleaf -> GitHub and U+FFFD.** In `computeDiff` (`diffEngine.ts`), a text file that still differs after the line-ending SHA check and whose Overleaf text contains U+FFFD gets one GitHub blob download (`ComputeDiffOptions.fetchBlobBytes`, `GitHubClient.getBlobBytes`; at most 100 per diff, 6 at a time). The blob is decoded with `decodeUtf8Text` and mapped with `toOverleafStorableText`; if that equals the Overleaf text (line endings normalized) the file is unchanged and GitHub's version stays, so a commit never swaps GitHub's emoji or Windows-1252 characters for U+FFFD. Otherwise it stays modified, and `DiffItem.warning` is set when the commit would write U+FFFD over other characters (or the blob could not be checked).
- **BOM.** Every `TextDecoder` that turns bytes into file or doc text uses `ignoreBOM: true` (`zipReader.ts`, `liveBridgeHandler.ts`, `sourceFromGitHubBranch.ts` and `diffEngine.ts` through `decodeUtf8Text` in `lineEndings.ts`, `commitEngine.ts`, `localFolderAccess.ts`). The default decoder drops a leading U+FEFF, which makes the text differ from the bytes and from the Overleaf doc, shifts every OT position by one, and makes every BOM file look modified. `decodePackedUtf8` is the strict variant for `joinDoc` lines.
- **Layout.** `src/background/`: the service worker. `src/content/`: the content script (`overleafContentScript.ts` dispatches, `liveBridgeHandler.ts`, `socketIo09.ts`). `src/popup/` and `src/options/`: the two React pages; the Options developer panels (write-back test, pull test) show only while their toggles are on. `src/overleaf/`: project detection (`overleafContext.ts`), the ZIP client and `live/` (bridge protocol, client and session, project loader, OT diff, write-back, conflict check, pull lock). `src/github/`: the REST client and the commit engine. `src/sources/`: the snapshot sources and the pull helpers. `src/diff/`: diff, hashing, ignore rules, `.gitignore` matching. `src/zip/`, `src/storage/`, `src/shared/` (types, constants, line endings, concurrency). `src/localReplica/`: not wired in.
- `src/offscreen/` is reserved for future use and is not referenced in the manifest.

## Commands

- `npm ci`: install dependencies.
- `npm run typecheck`: `tsc --noEmit`.
- `npm run build`: typecheck, then build into `dist/`. Load `dist/` unpacked in Chrome, never the repo root (it has no `manifest.json` on purpose).
- There are no automated tests. CI runs typecheck + build only. A behavior change needs a manual run against a real Overleaf project (see **Manual testing checklist**). Report what you verified and what you couldn't.
- There is no pre-commit hook. Run `npm run build` before every commit that touches `src/`.

## Versioning and releases

- The version lives only in `package.json` and `package-lock.json`. Bump it with `npm version <x.y.z> --no-git-tag-version`. `manifest.config.ts` derives the Chrome version and strips SemVer pre-release suffixes, which Chrome rejects.
- Pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml`. It fails if the tag doesn't match `package.json`, builds, strips source maps and attaches `overleaf-snapshot-to-github-vX.Y.Z.zip` to the GitHub release. Tags containing `-` are published as pre-releases.
- The Chrome Web Store upload is manual. Use the release ZIP from the GitHub release, never a local `dist/` (it has source maps).
- The license is AGPL-3.0-or-later. `npm version` does not update the lockfile's root `license` field, so change both files if you ever touch it.

## Overleaf protocol: confirmed facts

Overleaf's realtime and upload APIs are undocumented. Each point below was confirmed against a real project. Don't "fix" them back.

- **Socket.IO 0.9 acks are err-first** (`[err, ...data]`). `SocketIo09Client.emitWithAck` (`src/content/socketIo09.ts`) strips `err`, so callers receive the data starting at index 0.
- **Connecting.** `GET /socket.io/1/?projectId=<id>&t=<ms>` answers `<sid>:<heartbeat>:<close>:<transports>`, then the WebSocket opens at `/socket.io/1/websocket/<sid>?projectId=<id>`. Depending on the server, the project arrives in the ack of a `joinProject` emit (`[{ project_id }]`, ack `[project, permissions, protocolVersion]`) or in a `joinProjectResponse` event; `awaitJoinProject` handles both.
- **Reading and writing a doc.** `joinDoc` with `[docId, { encodeRanges: true }]` acks `[lines, version, updates, ranges]`. `applyOtUpdate` with `[docId, { op, v }]` works both for seeding an empty doc (one insert at v0) and for an update at v>0 (one delete and one insert); a fresh `joinDoc` afterwards gives the new version and text for the verify.
- **Creating folders and docs.** `POST /project/:id/folder` and `POST /project/:id/doc` take JSON `{ parent_folder_id, name }` with `X-Csrf-Token` and return the new entity with its `_id`.
- **Reading an uploaded file.** `GET /project/:id/file/:fileId` with `credentials: 'include'` returns its bytes.
- **`joinDoc` lines arrive latin1-packed; decode them.** The server sends `unescape(encodeURIComponent(line))`, an encoding on top of the WebSocket frame, so the browser's frame decode does not undo it. `decodePackedUtf8` in `src/content/liveBridgeHandler.ts` unpacks the lines and throws on anything that isn't packed UTF-8. `applyOtUpdate` ops are sent unpacked, so writes need no encode. Dropping the decode (as 1.1.1 briefly did) makes every non-ASCII doc look modified, and verify-after-write then fails on every write. The size difference matches UTF-8 bytes vs UTF-16 length.
- **Docs never hold `"\r"`.** Overleaf's document-updater splits text on `/\r\n|\n|\r/`, so a CRLF or lone-CR file read back is exactly as many characters shorter as it had `"\r"` characters (seen on real CRLF `.html` files and a CR-only `.cls`). Without normalizing, every pull rewrote each such file and then failed verify-after-write, and every new one failed its read-back. Normalize both sides (see **Line endings**).
- **Docs can't hold characters outside the BMP or lone surrogates.** document-updater `UpdateManager._sanitizeUpdate` does `op.i = op.i.replace(/[\uD800-\uDFFF]/g, '\uFFFD')` on every insert, per UTF-16 code unit, so an emoji (a surrogate pair) becomes TWO U+FFFD and the doc keeps the same length in code units (OT positions stay valid). Seen on a real project: an `.html` file had a loudspeaker emoji on GitHub and two U+FFFD in Overleaf. Without handling it, every pull saw a difference, wrote, and failed verify-after-write, forever. Compare, write and verify the storable text (see **Characters Overleaf can't store**).
- **Upload fields:** `POST /project/:id/upload?folder_id=<id>` expects multipart fields `relativePath` (the literal string `"null"`), `targetFolderId`, `name`, `type` (MIME) and `qqfile`. The fineuploader set (`qqfilename`, `qquuid`, ...) gets a 422 `invalid_filename`. Send `X-Csrf-Token` and `X-Requested-With: XMLHttpRequest`. The field names were taken from Overleaf's own drag-and-drop upload in DevTools. A 0-byte file with an image extension (a `touch`ed `.png`) gets the same `invalid_filename`, apparently because its content doesn't match its extension; the dispatcher lets an empty payload through so that Overleaf's answer reaches the user.
- **Socket and write calls go through the content script.** Overleaf rejects a socket opened from the extension origin, so every socket call, REST write and upload runs in the content script on the Overleaf tab. The bridge is `src/overleaf/live/bridgeProtocol.ts` -> `bridgeClient.ts` / `bridgeSession.ts` -> `src/content/liveBridgeHandler.ts`. The ZIP download is the exception (see **ZIP download**).
- **The content script can be injected more than once** (auto-inject on `protocol_unavailable`). The `window.__overleafGithubSnapshotBridgeLoaded` guard in `src/content/overleafContentScript.ts` keeps message handlers from registering twice. Without it, docs and uploads get created twice in Overleaf. Keep it, and put any new top-level setup in `overleafContentScript.ts` inside it, or that setup runs again on every injection.
- **The ZIP export sometimes answers 5xx** for a moment. The ZIP gate then stops the pull before anything is written, as it should; nothing retries yet (see **Backlog**). Never suggest turning the ZIP check off as a workaround: it is the user's way back.
- **Overleaf Workshop (AGPL-3.0)** is the reference for protocol vocabulary. Don't copy its code verbatim. When it and this code disagree, check Overleaf's own source (`overleaf/overleaf`, `services/real-time`) before changing either.

### Known limits

A doc renamed in Overleaf between the preview and the confirm gets the content of its old path: the write follows the doc ID, which was resolved from the path in the project tree read when the session opened. The conflict check compares text by doc ID, so it does not notice. A move or rename of a folder that is seen on the session socket re-reads the tree before a create or upload, but not before a replace.

A doc or file that a pull creates may not appear in the open Overleaf tab's file tree until the tab is reloaded (seen in 1.1.0; it is there). Uploads travel as one base64 message from the popup to the content script: a 207 KB image works, but files of tens of MB may hit Chrome's messaging limits.

With **Make Overleaf match GitHub exactly**: names are compared in Unicode NFC, but only that: a name that differs in anything else (case, a look-alike character) is a different file, and when two Overleaf entries are NFC-equal to one GitHub name, the pull writes to the one spelled exactly like GitHub's and keeps the other, or leaves the name alone if neither is spelled exactly the same. NFC matching applies to every pull, not only this mode. The repository's `.gitignore` is honoured for common syntax only (no `core.excludesFile`, no `.git/info/exclude`, no `!` exceptions, case-sensitive; a POSIX class like `[[:digit:]]` matches any one character, which keeps more), and the extension's own ignore patterns keep their simple matching (no folder patterns). A path where GitHub has a submodule or a symbolic link keeps everything Overleaf holds there, so stale files under it are never cleaned. The 50% and top-folder checks are heuristics: a project that really has most of its files only in Overleaf is refused until they are committed or removed. `linkedFileData` (a linked file) and `rootDoc_id` are read from joinProject as `services/web` `ProjectEditorHandler` sends them, not yet confirmed on a real project; if Overleaf omits one, its preview warning is simply absent. A GitHub file whose extension the extension doesn't read as text, but which Overleaf keeps as an editable doc, is neither replaced nor deleted (the pull leaves it out as an existing file). The destructive checks compare the session's tree, re-read when it is more than 15 s old or after a rename or move was seen, so one entity swapped for another at the same path inside that window, with no rename event and no change in Overleaf's listing, is not noticed (a doc delete still checks the text and a file replace the bytes; a file delete goes by ID, so a swapped file gets a 404 instead of being deleted).

## Overleaf protocol: read from source, not yet confirmed on a real project

From `overleaf/overleaf` (`services/real-time`: `Router.js`, `WebsocketController.js`, `DocumentUpdaterController.js`, `WebApiManager.js`; `services/web`: `ProjectUploadController`, `ProjectEntityMongoUpdateHandler`, `ProjectController.projectEntitiesJson`). Move a point up to the confirmed list once a real run backs it.

- **joinProject is the expensive, rate-limited step.** The server joins on connect via web's `/project/:id/join`; over the limit it emits `connectionRejected` ("rate-limit hit when joining project") and disconnects. `awaitJoinProject` fails fast on that event instead of waiting out its timer. Opening a socket per operation is what tripped this.
- **The applyOtUpdate ack means "queued", not "applied".** The sender then gets `otUpdateApplied` with only `{ v, doc }`, or `otUpdateError` followed by a disconnect. Writes wait up to 5 s for one of these before the verify read.
- **A doc-updater error disconnects every socket that joined that doc**, as does a rejected `applyOtUpdate`. Long-lived sessions must expect to reconnect. The `otUpdateError` sent with it can come from any update to the doc, so it is no verdict on ours: only an error ack means the update was refused, and otherwise the verify read decides.
- **`leaveDoc` is a no-op** on current real-time. Sessions don't send it: on older builds it could cancel a joinDoc still in flight on the same socket.
- **The upload route replaces** an existing entry of the same name (`uploadFile` adds the entity with `replace=true`), which is why uploads re-check a fresh listing.
- **A taken name is refused** on POST `/folder` and `/doc` with HTTP 400 "file already exists" (`DuplicateNameError`). `isNameTakenError` relies on that text.
- **Delete routes** (`services/web` `EditorRouter`, `EditorHttpController._deleteEntity`, all `ensureUserCanWriteProjectContent`): `DELETE /project/:id/doc/:entity_id`, `/file/:entity_id` and `/folder/:entity_id`, answering 204; the CSRF token goes in `X-Csrf-Token` like the POSTs. `EditorController.deleteEntity` removes a folder with everything in it, and broadcasts `removeEntity` on the project room (our own socket gets it too). The deleted entities stay recoverable from the project's History.
- **A replaced or deleted file ID answers 404** on `GET /project/:id/file/:file_id`: it is no longer in the tree.
- **A same-name upload replaces with a new ID.** `ProjectUploadController` -> `upsertFile`: an existing file of that name is replaced by `_replaceFile` (new file ID, the old one goes to History), an existing doc is converted to a file (`convertDocToFile`) and, the other way round, a file replaced by editable content can become a doc (`convertFileToDoc`). The upload reply carries `entity_id` and `entity_type`.
- **`GET /project/:id/entities`** returns `{ project_id, entities: [{ path: '/main.tex', type: 'doc' | 'file' }] }`.

## Safety invariants

- Never read `document.cookie` or request `chrome.cookies`. Overleaf requests use `credentials: 'include'`.
- The GitHub token is sent only to `api.github.com` and never reaches the content script.
- The ref update is always non-forced (`commitEngine.ts` passes `force: false`).
- A snapshot with warnings disables deletions (`effectiveIncludeDeletions` in `src/popup/PopupApp.tsx`). A file that failed to fetch must never become a GitHub deletion.
- Every write needs an explicit click, and a pull writes only what its preview listed. `applyPullPlan` never re-reads GitHub and uses the plan's read as the conflict base. The typed `replace` confirmation (`requireConfirmationBeforeWriteBack`, `pullNeedsTypedConfirmation`) guards every pull that replaces an existing doc.
- Overleaf writes pass the gates listed under **Write paths and their gates**. Binary upload is create-only: existing files are skipped, never deleted and re-uploaded. A pull never deletes anything in Overleaf. These two hold except in one explicitly confirmed mode, **Make Overleaf match GitHub exactly** (off by default, never turned on by the extension itself): only there may a pull replace an uploaded file or delete a doc, an uploaded file or a folder, only for items its preview listed, only after the typed `delete` (`delete N` for a large deletion), and only through the extra checks under **Write paths and their gates**. Anything on GitHub (in the full tree, by NFC name), anything matching the ignore patterns or the repository's `.gitignore`, and anything at or under a GitHub submodule or symbolic link is never deleted. The helpers that carry out replacements and deletions are private to `pullFromGitHubHelpers.ts`: the only way in is `applyPullPlan`, which checks the typed word first. Deleted and replaced files stay in Overleaf's History.
- Pull from GitHub into Overleaf (the `experimentalLiveSyncEnabled` master switch with `overleafWriteBackEnabled`) is on by default, by the owner's decision. It stays behind the preview and the typed `replace` confirmation. The other live sync features (`liveReadOnlyPullEnabled`, `localReplicaEnabled`) stay off by default, each behind its own toggle. Keep the ZIP backup and typed confirmation enabled by default, and keep binary write-back and "Include all file types" disabled by default. A new feature behind a toggle starts off.
- Diagnostics (`localStorage['ofs-live-debug']='1'`) log structure only, never document text.
- A new permission or host permission is a user-visible change: installed users must approve it again at the next store update. Call it out and update README -> **Security**. Any change to what is stored or sent where must update `PRIVACY.md` in the same change.

## Conventions

- Conventional Commits with a scope (`feat(live-sync):`, `fix(content):`, `chore(release):`, ...; scopes in use: `live-sync`, `live`, `popup`, `options`, `content`, `sources`, `pull`, `zip-route`, `release`). One slice per commit: plumbing, UI and a developer panel go in separate commits, so each can be reverted alone. The commit body explains the root cause and how the change was verified.
- Don't push, force-push or push a tag without the owner's say-so: a `vX.Y.Z` tag publishes a release.
- Build risky protocol work in small steps: ship the smallest slice that can be tested, have it confirmed on a real project, then build on it. A new Overleaf route gets an Options developer panel test before the popup uses it, and its exact request is taken from Overleaf's own UI in DevTools, not guessed.
- Test destructive features (deletes, replacements) on a throwaway Overleaf project linked to a throwaway repository, never on a real one.
- A sub-option of a toggle that is off is hidden, not shown disabled.
- Bulk operations report each file's outcome. A file that fails doesn't stop the others (a lost tab does, and the rest read `not_attempted`).
- `extension photos/` holds the Chrome Web Store images. It stays untracked: don't commit or delete it.
- Keep `README.md` short and user-facing. Put architecture and protocol detail here. When user-visible behavior, permissions or modes change, update the README in the same change.
- User-facing text (UI, errors, README) is plain language, uses the label the user actually sees, and names no internal mechanism.

## Manual testing checklist

**Overleaf -> GitHub**

1. Non-Overleaf tab, with Manual ZIP upload on: the automatic button is hidden and manual ZIP still works. With it off, the popup shows the no-tab guidance and no ZIP picker.
2. Signed in: the ZIP route fetches, shows the diff and commits.
3. Signed out: the ZIP route fails with `not_logged_in`. With Manual ZIP upload on, the manual fallback appears; with it off, the error shows its sign-in advice and the tip about turning the setting on, and no picker.
4. With **Enable live sync** turned off and saved in Options, the popup shows no live UI. On a fresh profile (nothing saved) the popup shows the Pull from GitHub section and no Read-from-the-Overleaf-tab card.
5. **Read from the Overleaf tab** (live read-only) reads every doc and file, then shows the diff and commits.
6. Tab opened before an install or update: the first bridge call auto-injects the content script and succeeds without a refresh.
7. A snapshot with fetch warnings disables the deletions checkbox, and `onCommit` also forces `includeDeletions=false`.

**GitHub -> Overleaf**

8. With write-back turned off and saved in Options, there is no Pull-from-GitHub section. A fresh install shows it (on by default).
9. No GitHub-side change: the preview says there is nothing to pull and offers only OK; nothing is written.
10. One character changed in an existing `.tex`: the preview lists only that file (`+1 -1 lines`); the confirm button stays disabled until `replace` is typed; then only that file is `written` (exercises `applyOtUpdate` at v>0).
11. With "Also create new files", a new `.tex` is `created`, parent folders are created and the content is seeded.
12. With binary write-back and create both on, a new PNG is `uploaded` and existing binaries are `skipped`.
13. If the ZIP backup endpoint returns 5xx, the pull fails at the preview step with `write_back_not_safe` before any write and shows no preview. If the check only fails at confirm (the plan's check is older than 10 minutes), nothing is written either.
14. Options -> Developer write-back test: Read -> edit -> Write back returns `written`.
15. A pull on a larger project (dozens of docs) finishes without `joinProject did not respond` or rate-limit errors; with `localStorage['ofs-live-debug']='1'` the tab logs a single `phase: joinProject`.
16. Tab opened before an extension update: the pull stops with "Reload the Overleaf tab..." and writes nothing; after a reload it succeeds.
17. Edit a listed file in Overleaf while the preview is open, then confirm: that file ends as `conflict` and keeps the Overleaf edit; the others are `written`.
18. Leave the preview open for more than 3 minutes (the session idles out), then confirm: the pull completes. After more than 10 minutes a new ZIP backup is taken first.
19. With "Ask me to confirm before replacing files in Overleaf" off, or when the pull only adds new files, a single "Pull N files" click confirms.
20. Preview: it lists replaced files with line counts, added files, uploads, "already match" and the files left out with a reason, and the counts match the result afterwards. Planning writes nothing (Overleaf's History shows no new entry before the confirm).
21. Cancel on a preview changes nothing in Overleaf, and a new pull then starts without "another pull is running".
22. Typed confirmation: the confirm button stays disabled until `replace` is typed (trimmed, any case); it is not asked when the pull only adds files.
23. Overleaf pages show no extension button.
24. Line endings: a GitHub file with CRLF (and one with lone CR) that matches its Overleaf doc counts as already matching and is not in the replace list; changing one character in a CRLF file replaces only that file, and a second pull is a no-op; a new CRLF file is created and verified; an Overleaf -> GitHub fetch of unchanged CRLF repo files shows no diff.
25. Uploaded-file rows: a GitHub text file (for example `data.csv`) that Overleaf keeps as an uploaded file is listed under files not pulled with the uploaded-file reason, with "Also create new files" on or off. The result shows a "Not changed" row for it, never a failed create and never "not in Overleaf yet".
26. Create a doc in Overleaf at a path the preview planned to add, then confirm: that row reads "Not added: ...", not "Failed".
27. Start a pull in the popup and another for the same project from Options: the second is refused with "Another pull ... is already running".

**Popup display (Manual ZIP upload)**

28. Manual ZIP upload setting, both states. *Off (the default, also a fresh install or a profile that never saved the setting):* the ready view has no Manual ZIP upload section, even after **Fetch from current Overleaf project** fails; that failure's error view has no ZIP picker, shows a "What to try" line with a real remedy (or the message's own advice) and "You can also turn on Manual ZIP upload in Options."; with no Overleaf tab open (and at least one linked project) the popup shows the no-tab guidance and an **Open Options** button, not the project picker; a GitHub error shows no tip. *On:* the section appears after a failed fetch and with no tab open (the project picker comes back), the error view shows the inline picker, `project_too_large` / `project_empty` show none, and **Always show Manual ZIP upload** keeps the section visible on a healthy project. In Options -> Popup display, **Enable manual ZIP upload** saves on click, shows **Always show Manual ZIP upload** only while it is on, and a reload keeps both.

**Emoji, non-UTF-8 files and defaults**

29. Emoji: a GitHub file with an emoji (for example a loudspeaker) whose Overleaf doc holds two U+FFFD at that spot counts as already matching (note about characters Overleaf can't store) and a second pull writes nothing; change one other character in it, and only that line changes, the row is `written` with the note, verify passes and the emoji spot stays two U+FFFD. A new file containing an emoji is created and verified.
30. Non-UTF-8: a GitHub text file saved as Windows-1252 (curly quotes, bytes 0x93 and 0x94). If Overleaf holds the U+FFFD form, the pull says it already matches (note) and offers nothing; if Overleaf holds anything else, or has no such doc, it is left out with the "isn't saved as UTF-8 text" reason in the preview and in the result, and nothing is written or created.
31. Overleaf -> GitHub with the two files above: a fetch shows them unchanged (GitHub's emoji and Windows-1252 bytes stay), a genuine edit to one still shows as modified, and a commit that would write U+FFFD over other characters shows the warning on its row.
32. Options on a fresh profile: **Enable live sync** and **Enable Overleaf write-back** are ticked with the write-back settings expanded (ZIP check and typed confirmation ticked, binary uploads and all file types unticked), **Read from the open Overleaf tab** and **Local replica** are unticked, and the section has no intro banner.

**Make Overleaf match GitHub exactly**

33. Option off (the default for every project; also a fresh profile, and settings saved when the option was one global flag): a pull has no deletion or uploaded-file replacement in its preview, nothing in Overleaf is deleted or re-uploaded, and `.gitignore` held as an uploaded file is still listed as left out. The popup and the Options pull test panel show the checkbox unticked with the hint ("Also deletes files not on GitHub and replaces uploaded files that differ. You'll type delete to confirm.").
34. Tick it (popup, then reopen the popup, and Options): it stays ticked for that project only (another project's popup shows it unticked, and so does the Options project selector), the pull button reads "Pull and match GitHub" while it is ticked (grey, a red outline on hover), "Also create new files in Overleaf" shows ticked and disabled. Preview on a project with a doc that exists only in Overleaf (for example `docs/x.html`) and an uploaded `.gitignore` older than GitHub's: the preview lists "Will be deleted from Overleaf (N)" and "Uploaded files that will be replaced (N)" (plus the usual replaced, added and uploaded lists), mentions Overleaf's History, and Overleaf's History shows no new entry before the confirm. Confirm stays disabled until `delete` is typed (trimmed, any case), also with "Ask me to confirm before replacing files in Overleaf" off. After the confirm, Overleaf holds the same files as GitHub (plus the kept files: build files such as `.aux`, ignore-pattern matches, anything the repository's `.gitignore` excludes), `.gitignore` is still an uploaded file with GitHub's bytes, folders that were empty or left empty are gone, and History shows the deleted and replaced files.
35. Deleting more than 20 files, or more than 30% of the project's files, shows a red warning with the count and asks for `delete N` with the exact number; `delete` alone does not work.
36. Uploaded files with the same bytes as GitHub's (images, a `.gitignore` that already matches) are not re-uploaded: their IDs are unchanged and History shows nothing for them.
37. Edit a doc that is listed under "Will be deleted" in Overleaf while the preview is open, then confirm: that doc stays with your edit and its row reads "Not deleted: ... edited in Overleaf after the preview"; its folder stays; the rest is deleted. Replace an uploaded file that is listed as "will be replaced" (upload another version by hand) and confirm: that row reads "Not replaced", your version stays.
38. GitHub files that the pull would otherwise leave out (an extension not in the allowed list, a PNG with binary uploads off, a text file saved as Windows-1252) are never deleted from Overleaf. Build files (`.aux`, `.log`, `.bbl`, `.synctex.gz`) and files matching the project's ignore patterns are kept and listed ("will be kept"), each group with its own reason (build files, your ignore patterns, the repository's `.gitignore`), and a user pattern is not called a build file.
39. With a target directory set: only files under it count as being on GitHub, so an Overleaf file that exists on GitHub only outside that folder is deleted. With the target directory wrong (the branch has nothing there, no Overleaf file shares a path with GitHub, fewer than half of the Overleaf files do, or every Overleaf file sits in one folder GitHub doesn't have around them), the pull stops with an error that names the cause and the target directory, and nothing is changed.
40. A repository too large for GitHub to list refuses the pull; an empty branch deletes nothing (the popup says "Nothing to pull").
41. With the ZIP backup on, a failing export stops a pull that only deletes before any file is touched. After more than 10 minutes with the preview open a new backup is taken at the confirm. If Overleaf answers a delete or an upload with a server error, the row says it is unknown whether it happened and to run the pull again; rerunning finishes the job. Cancel on the preview changes nothing. With an Overleaf tab opened before the extension update, the pull stops with the "reload the tab" message before anything is read.

42. Repository `.gitignore`: a PDF that Overleaf needs (for example a figure) and that the repository's `.gitignore` excludes (`*.pdf`) is kept and listed with "kept because the repository's .gitignore excludes it", also with the project mapped to a sub-folder of the repository (a `.gitignore` at the repository root still applies), and a `!` exception in that file does not make the pull delete it.
43. Submodule and symbolic link: with a GitHub submodule at `template/` (or a symlink at `figures`), the Overleaf files under that path are kept and listed ("inside a folder that GitHub has as a submodule" / "at or inside a path that GitHub has as a symbolic link"), none is deleted, and a symlink is listed as left out and never added or uploaded, also without the mirror option.
44. Accents: Overleaf has `ü` as one character (typed in the editor) and GitHub has it as `u` plus a mark (pushed from a Mac): the file counts as already matching or is replaced under Overleaf's name, is never deleted and never added a second time.
45. Wrong mapping: with every Overleaf file inside one folder that GitHub lacks (the ZIP route's top-folder case), or with fewer than half of the Overleaf files on GitHub, the mirror pull stops before anything is read for deletion, and says the target directory may be wrong.
46. Preview warnings: a linked file (imported from a URL or another project) whose upload would replace it is noted as becoming a plain uploaded file, and a plan that deletes the project's main document shows a red warning naming it. (Both rely on Overleaf sending `linkedFileData` and `rootDoc_id` in joinProject, not yet confirmed on a real project: report whether they showed.)
47. Repeated request: if a delete or replace row would read "Not deleted / Not replaced" only because the popup sent the request again after "message port closed", it reads "Deleted" / "Replaced" with "Confirmed on a second check". A file deleted by hand after the preview still reads "Not deleted".

Not implemented: binary replace outside **Make Overleaf match GitHub exactly** (which replaces uploaded files by uploading GitHub's bytes), deleting files in Overleaf outside that option (a pull never does; a commit deletes on GitHub only with "Include deletions"), and local-replica UI.
